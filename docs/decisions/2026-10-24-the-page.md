# The page: how the showcase runs in the browser (2026-10-24)

The core library gives the FFmpeg path's results on browser-wasm (README, Checks). This decides how the page around it
is built, before any of it is written. The owner's earlier decisions (a new repository, plain HTML + JSExport, decoding
in a web worker, FastYuv its own DLL, the first version's scope) are in shotdetector's
[docs/decisions/2026-10-24-managedcodecs-showcase.md](https://github.com/bisforboman/shotdetector/blob/main/docs/decisions/2026-10-24-managedcodecs-showcase.md)
and are not reopened here. The work itself is in [../backlog.md](../backlog.md).

## Where the runtime lives and what crosses the boundary

### Question

The owner decided: decoding in a web worker, `[JSExport]`. What exactly does the main thread send the worker, and what
comes back?

### Choices

1. **The worker owns the .NET runtime; the main thread owns the DOM; strings cross.** `worker.js` starts `dotnet.js`,
   gets the exports of `ShotDetectorWeb.App`, and answers two messages: `open` (the file's bytes) and `detect` (the
   options as JSON). The .NET side is one static class with `[JSExport]` methods: `Open(byte[])` returns the
   `YuvVideo` description as JSON (or throws; the message is the user's error text), `Detect(string optionsJson)`
   returns a JSON object holding what the page shows and downloads, every piece made by ShotDetector itself:
   `Shots.Json(result.Shots)`, `Shots.Csv(result.Shots, cuts: result.Cuts)`, `result.Stats.Csv(...)`, the frame count,
   the frame rate and the duration. Progress goes the other way through one `[JSImport] progress(done, expected)` that
   `worker.js` turns into a `postMessage`.
2. **Typed objects across the boundary**: marshal `Shot`, `FrameTime`, options as .NET objects to JS.

### Answer

**1.** ShotDetector already serializes everything the page needs; the page parses JSON. One import, two exports, no
marshalling code to keep right. A `postMessage` from inside synchronous .NET code is delivered: the worker's own event
loop is blocked while `Detect` runs, the main thread's is not, so progress arrives while the run is going.

## Cancelling a run

### Question

`ShotDetection.Detect(YuvVideo, ...)` is synchronous and the worker's event loop is blocked while it runs: a `cancel`
message can never reach the worker to trip the `CancellationToken`. How does the user stop a run?

### Choices

1. **`worker.terminate()` and start a fresh worker.** The runtime starts again (about a second) and the file is sent
   again on the next run.
2. **Cooperative cancelling**: make the frame enumeration yield to the event loop every N frames so a message can
   arrive. Needs an asynchronous `Detect` over a frame source, which ShotDetector doesn't have, or a hand-rolled pump.

### Answer

**1.** One line, and it also recovers from a runtime that has crashed. The restart cost is paid only when the user
cancels. The page's state machine has an *opening* state besides *detecting*: `Mp4Input`'s constructor decodes to the
first frame and walks every packet for the format's duration, so on a big file there is a visible pause before the
first progress report.

## Which errors are the file's fault

### Question

The page row shows errors in the words the library threw, ManagedCodecs' `InvalidDataException` (a damaged file)
prefixed "The file is damaged or not an MP4 this page can read:", the core's `UnsupportedVideoException` (a file
outside the scope) as it is. A .NET exception reaches JavaScript as an `Error` with the message and the managed stack
trace, not the type (seen 2026-10-24 under Node: a ManagedCodecs `InvalidDataException` and the core's
`UnsupportedVideoException` look the same apart from their stack frames). How does the page tell them apart?

### Choices

1. **`Api` prefixes it**: `Open` and `Detect` catch `InvalidDataException` and throw it again with the prefix, the
   original as its inner exception. The page shows every message as it comes.
2. **The kind crosses as data**: the exports return `{ error: { kind, message } }` instead of throwing, or a second
   export says what the last exception was; the page holds the words.
3. **The page reads the stack**: a top frame in `ManagedCodecs.` means damaged. ManagedCodecs also throws
   `NotSupportedException` (a feature it doesn't decode), which would be called damaged, and stack frames are a
   debugging aid, not a contract.

### Answer

**1.** Six lines in `Api`, the exports' contract unchanged (throw on failure, the message is the user's text), and no
type name has to cross. The words sit in .NET beside the one place that knows the type; the page row's "nothing but
`index.html`, `app.js`, `style.css`" makes this one exception, said in its pull request.

## The file in memory

### Question

`Mp4Input.Open(byte[])` copies the whole file into the wasm heap, and every enumeration opens the stream again. What
size is too big?

### Choices

1. **Whole file in memory, refuse above 512 MB** with a message saying the page is for trailers, not films (the
   decision doc's scope), and that larger files are coming.
2. **Stream the file**: `Mp4Input` already takes a `Func<Stream>`, and workers have `FileReaderSync`, so a
   `BlobStream` reading slices synchronously is possible without touching the core library.

### Answer

**1 now, 2 next** (backlog: "Large files"). The limit is one `if`; the stream is a class with a check of its own, worth
doing once the page exists. The limit is a knob in `app.js`, not a constant anyone has to find.

## Delivery

### Question

A browser-wasm publish is tens of megabytes raw. GitHub Pages serves static files as they are and sets no headers of
ours. How does the bundle ship?

### Choices

1. **Compiled ahead of time, trimmed, measured first; then compress only if Pages doesn't.** If Pages gzips
   `application/wasm` on the fly, nothing to do. If not, publish pre-compressed `.gz` files next to the originals and
   give `dotnet.js` a resource loader (`withResourceLoader`) that fetches the `.gz` and inflates it with the browser's
   own `DecompressionStream('gzip')`: no library. Brotli would be smaller but `DecompressionStream` doesn't do it and
   a JS decoder is a dependency.
2. **Ship raw** and accept the size.
3. **Another host** that negotiates content encoding.

### Answer

**1.** Pages is the owner's choice and costs nothing. The backlog row carries the numeric target (first load at most
8 MB transferred) and records the measured sizes in the README. Trimming today keeps FFmpeg.AutoGen; ShotDetector's
package isn't marked `IsTrimmable`, which is the likely reason (a trim mode that leaves unmarked assemblies whole),
but the publish log is the authority: whether `TrimMode=full` is safe or ShotDetector should opt in upstream is its
own row.

Whatever the compression, the LGPL layout holds in the published `_framework/`: `ShotDetector.FastYuv.wasm` is its
own file (no single-file, no merged AOT) and `licenses/ShotDetector.FastYuv/COPYING.LGPL` is in the Pages artifact; the
deploy row checks both from the published listing.

## Threads

### Question

ManagedCodecs decodes on several threads if asked, and ShotDetector scores chunks in parallel. Can the page use that?

### Choices

1. **No: single-threaded.** Wasm threads need `SharedArrayBuffer`, which needs COOP/COEP headers, which Pages cannot
   set.
2. **A service worker that adds the headers** (the `coi-serviceworker` trick) and a multithreaded runtime build.

### Answer

**1**, and 2 is a Maybe row with its enabler named. On one thread a trailer takes a few times real time on a laptop
(ManagedCodecs at 2.3 to 3.6 times FFmpeg's time), which is what the scope promised.

## The page itself

### Question

What is on the page, and with what?

### Choices

1. **One `index.html`, one `app.js`, one `style.css`, no build step, no framework, no dependencies.** A file picker
   that also takes a drop; the detector (adaptive, content, threshold, histogram, hash) with its threshold prefilled
   from ShotDetector's default, and the minimum shot length; a "Try the demo" button; opening and progress states with
   a cancel; the shots in a table (number, start, end, length), each row seeking a `<video>` element that plays the
   original file (the browser decodes for playback; exactness is about the numbers, not the picture); downloads of the
   scenes CSV and the stats CSV, named after the file; errors shown in the words the library throws. A footer: what
   runs where, that nothing leaves the machine, the licenses.
2. **A component framework** (Blazor was declined by the owner; React, Lit and the like are a build step).

### Answer

**1.** A visitor should read the page's source and see the whole thing. Stats are always collected (that is the
scenedetect `-s` output the exactness check compares; its memory is a few hundred bytes a frame).

## One wasm project

### Question

`tools/WasmCheck` is a browser-wasm executable run under Node that detects on the samples. The page needs another
browser-wasm project with `[JSExport]`. Two?

### Choices

1. **One: `src/ShotDetectorWeb.App` replaces WasmCheck.** Its `Program.cs` only keeps the runtime alive; the `Api`
   class holds the exports. `tools/check.sh wasm` publishes the App and runs `tools/app-check.mjs` under Node, which
   calls the same `Open` and `Detect` exports the worker calls, on every sample and run, and writes the CSVs the native
   check compares. The FFmpeg-not-loaded check becomes an export too (`LoadedAssemblies()`).
2. **Two projects**: WasmCheck as it is, the App beside it.

### Answer

**1.** The exactness check then runs the page's own entry points, so the thing deployed is the thing checked. Node
runs `getAssemblyExports` as the browser does; WasmCheck already proves `[JSImport]` under Node.

## The demo clip

### Question

The owner wants a clip on the page. Which, and where does it come from?

### Choices

1. **Sintel's trailer (Blender Foundation, CC-BY 3.0), built at deploy time.** The Pages workflow downloads the
   original from download.blender.org pinned by SHA-256 and re-encodes it with a recipe added to
   `tools/make-samples.sh` (today `SINTEL=` only copies a file it names `sintel_trailer-480p.mp4`): 8-bit 4:2:0
   progressive H.264, constant rate, 480p (854x480), around 10 MB. CI runs the same recipe, so the exactness check
   covers the very file the demo runs. The page credits it.
2. **The clip committed to the repository** (plain or LFS; Pages doesn't serve LFS objects).

### Answer

**1.** No binary in git, one recipe for the check and the demo. If the download ever goes away the deploy fails
loudly and the row says what to do (commit the re-encoded file then).

Should the page show a still per shot?

### Choices

1. **Later, from the browser's `<video>`**: seek, `drawImage` to a canvas. No second decode, no exactness question.
2. **From ManagedCodecs' frames**, converted to RGB in .NET and sent over.

### Answer

## Testing the page

### Question

The exactness checks cover the library, and with "One wasm project" the App's exports. What checks the page?

### Choices

1. **Nothing automated in the first release; a Playwright smoke test next**: CI serves the published bundle, loads the
   page in Chromium, sets the file input to one sample, clicks detect, downloads the scenes CSV and compares it with
   the native check's.
2. **Playwright from the start.**

### Answer

**1.** The page is a few hundred lines of JS around checked exports; the browser test earns its CI minutes once the
page exists and is being changed.

## Not doing

- **WebCodecs** (the browser's own H.264 decoder) as a faster path: its output differs between browsers and from
  FFmpeg's, which is the one thing this showcase is about.
- **Exports of clips or images through ShotDetector's `Export`**: it needs ffmpeg.
- **Analytics, a backend, uploads**: nothing leaves the machine; the page says so.
