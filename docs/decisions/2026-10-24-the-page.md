# The page: how the showcase runs in the browser (2026-10-24)

The core library gives the FFmpeg path's results on browser-wasm (README, Checks). This decides how the page around it
is built, before any of it is written. The owner's earlier decisions (a new repository, plain HTML + JSExport, decoding
in a web worker, FastYuv its own DLL, the first version's scope) are in shotdetector's
[docs/decisions/2026-10-24-managedcodecs-showcase.md](https://github.com/bisforboman/shotdetector/blob/main/docs/decisions/2026-10-24-managedcodecs-showcase.md)
and are not reopened here. The work itself is in [../backlog.md](../backlog.md).

## Where the runtime lives and what crosses the boundary

### Question

The owner decided: decoding in a web worker, `[JSExport]`. What exactly does the main thread send the worker, and what
comes back?

### Choices

1. **The worker owns the .NET runtime; the main thread owns the DOM; strings cross.** `worker.js` starts `dotnet.js`,
   gets the exports of `ShotDetectorWeb.App`, and answers two messages: `open` (the file's bytes) and `detect` (the
   options as JSON). The .NET side is one static class with `[JSExport]` methods: `Open(byte[])` returns the
   `YuvVideo` description as JSON (or throws; the message is the user's error text), `Detect(string optionsJson)`
   returns a JSON object holding what the page shows and downloads, every piece made by ShotDetector itself:
   `Shots.Json(result.Shots)`, `Shots.Csv(result.Shots, cuts: result.Cuts)`, `result.Stats.Csv(...)`, the frame count,
   the frame rate and the duration. Progress goes the other way through one `[JSImport] progress(done, expected)` that
   `worker.js` turns into a `postMessage`.
2. **Typed objects across the boundary**: marshal `Shot`, `FrameTime`, options as .NET objects to JS.

### Answer

**1.** ShotDetector already serializes everything the page needs; the page parses JSON. One import, two exports, no
marshalling code to keep right. A `postMessage` from inside synchronous .NET code is delivered: the worker's own event
loop is blocked while `Detect` runs, the main thread's is not, so progress arrives while the run is going.

## Cancelling a run

### Question

`ShotDetection.Detect(YuvVideo, ...)` is synchronous and the worker's event loop is blocked while it runs: a `cancel`
message can never reach the worker to trip the `CancellationToken`. How does the user stop a run?

### Choices

1. **`worker.terminate()` and start a fresh worker.** The runtime starts again (about a second) and the file is sent
   again on the next run.
2. **Cooperative cancelling**: make the frame enumeration yield to the event loop every N frames so a message can
   arrive. Needs an asynchronous `Detect` over a frame source, which ShotDetector doesn't have, or a hand-rolled pump.
3. **A shared flag**: the page sets a `SharedArrayBuffer` flag and the worker reads it with `Atomics.load` in the
   `progress` import, which then cancels the token. About ten lines and no ShotDetector change, but shared memory
   needs cross-origin isolation (COOP/COEP headers), which Pages can't set: it needs the `coi-serviceworker` trick
   from "Threads".

### Answer

**1.** One line, and it also recovers from a runtime that has crashed. The restart cost is paid only when the user
cancels. The page's state machine has an *opening* state besides *detecting*: `Mp4Input`'s constructor decodes to the
first frame and walks every packet for the format's duration, so on a big file there is a visible pause before the
first progress report.

**Next: 2**, the owner's choice (2026-10-24), through ShotDetector 3.15.0's asynchronous frame-source `DetectAsync`
(backlog: "Stop a run and keep what was read, without restarting the worker"). It keeps the runtime and the opened file, so a second run with
another threshold starts at once, and an asynchronous frame source serves every ShotDetector user, not just this page.
`worker.terminate()` stays for a runtime that has crashed. A cancelled token keeps no result (ShotDetector throws
`OperationCanceledException`), so the page's button becomes Stop (the owner's question, 2026-10-26): the frame source
ends where the run has got to, and `DetectAsync` finishes with the result for the frames read, stats included. Until
then, the page keeps the shots `DetectionOptions.OnShot` told it as they were found (backlog: "Shots as they're
found"), which works with `terminate()` too.

**Done** (2026-10-25, "Shots as they're found"): `Api` tells each shot through a `[JSImport] shot(json)` (one object of
`Shots.Json`'s array), `worker.js` posts it, `app.js` adds the row. On Cancel the worker is still terminated; the rows
stay, with one line marked unfinished from the last shot's end to the frame of the last progress report (the page's own
times, not a shot), and no downloads, as .NET is gone with the worker.

**Done: 2** (2026-10-26, "Stop a run and keep what was read"). `Mp4Input.FramesAsync` awaits the host every 8 frames
(`Api`'s `PauseEvery`) through a `[JSImport] pause`, a promise resolved by a `MessageChannel` message in the worker's
next task (`wwwroot/pause.js`; nested `setTimeout(0)`s are held to 4 ms each), so the worker's messages run between
frames. The page's button is Stop: `worker.js` calls `Api.Stop` at once on a `stop` message, the frames end at the next
pause, and `Detect` answers with the result for the frames read (`stopped: true`), shots and both CSVs, shown and
downloadable as a finished run's are, labelled "stopped at". ShotDetector 3.16.1 neither warns nor refuses when fewer
frames come than `YuvVideo.FrameCount` says: a run's `FrameCount` is the frames read, its last shot ends there. The
token cancels a run the page abandons (a new file picked during it: `cancel`, answered `cancelled`, no result kept), and
`terminate()` stays for a worker that doesn't answer a stop within a second plus a few pauses. The next run starts at
once on the opened file. A pause takes 6 µs in Chromium's worker; under Node the pauses cost 0.05% of the runs interpreted and 0.25% compiled ahead of time
(`tools/app-check.mjs` fails above 1%; README "Stopping a run").

## The file in memory

### Question

`Mp4Input.Open(byte[])` copies the whole file into the wasm heap, and every enumeration opens the stream again. What
size is too big?

### Choices

1. **Whole file in memory, refuse above 512 MB** with a message saying the page is for trailers, not films (the
   decision doc's scope), and that larger files are coming.
2. **Stream the file**: `Mp4Input` already takes a `Func<Stream>`, and workers have `FileReaderSync`, so a
   `BlobStream` reading slices synchronously is possible without touching the core library.

### Answer

**1 now, 2 next** (backlog: "Large files"). The limit is one `if`; the stream is a class with a check of its own, worth
doing once the page exists. The limit is a knob in `app.js`, not a constant anyone has to find.

**2 is done** (2026-10-25, the large files row; the 512 MB limit and its message are gone). `worker.js` gets the `File`
itself (a structured clone, which copies no bytes) and passes it to `Api.Open(JSObject)`; `Mp4Input.Open(Func<Stream>)`
opens a new `BlobStream` (src/ShotDetectorWeb.App) for each pass, a seekable stream that reads slices of the `File`
through a `[JSImport] read` (`wwwroot/blob-read.js`: `FileReaderSync.readAsArrayBuffer(file.slice(...))`) into a buffer
of a megabyte. The demuxer reads each sample at its offset in file order, a few kilobytes at a time, so a megabyte is a
few hundred samples per call into JavaScript; a read as big as the buffer goes straight into the caller's memory. The
checks read the samples through the same `read` under Node (`tools/node-host.mjs`).

What the stream reads matters more than its buffer. Each `FileReaderSync` read returns a new `ArrayBuffer`, and V8 frees
them only late while .NET holds the worker's thread (it never returns to its event loop during `Open` or `Detect`):
reading a 2.37 GB file as fast as it comes (1 MB slices, about 170 MB/s in headless Chromium) grew the renderer to 1.2
to 1.4 GB, and three passes to 2.3 GB. A run reads at the decoder's pace (under 1 MB/s for a 640x360 film), where the
garbage is collected as it goes; the opening pass did not: `Mp4Input`'s constructor walked every packet for the format's
duration, and ManagedCodecs' demuxer read each packet's data, which that pass never looks at (43 s and a 1.7 GB renderer
peak on that file). It now skips those reads (`TimingOnlyStream` in `Mp4Input`, past the demuxer's constructor), and
opening takes 3.4 s. Each read also costs about 2.4 ms whatever its size (64 KB slices read at 25 MB/s, 1 MB at 170, 4
MB at 290), so the buffer stays at a megabyte: at a run's pace that is well under 1% of the time. Measured in README,
"Large files".

## Delivery

### Question

A browser-wasm publish is tens of megabytes raw. GitHub Pages serves static files as they are and sets no headers of
ours. How does the bundle ship?

### Choices

1. **Compiled ahead of time, trimmed, measured first; then compress only if Pages doesn't.** If Pages gzips
   `application/wasm` on the fly, nothing to do. If not, publish pre-compressed `.gz` files next to the originals and
   give `dotnet.js` a resource loader (`withResourceLoader`) that fetches the `.gz` and inflates it with the browser's
   own `DecompressionStream('gzip')`: no library. Brotli would be smaller but `DecompressionStream` doesn't do it and
   a JS decoder is a dependency.
2. **Ship raw** and accept the size.
3. **Another host** that negotiates content encoding.

### Answer

**1.** Pages is the owner's choice and costs nothing. The backlog row carries the numeric target (first load at most
8 MB transferred) and records the measured sizes in the README. Trimming today keeps FFmpeg.AutoGen; ShotDetector's
package isn't marked `IsTrimmable`, which is the likely reason (a trim mode that leaves unmarked assemblies whole),
but the publish log is the authority: whether `TrimMode=full` is safe or ShotDetector should opt in upstream is its
own row.

Measured on the live site (2026-10-24, README "Size"): Pages gzips every response, `application/wasm` and the ICU
`.dat` included, so the first case holds and nothing is pre-compressed. The first load was 5.98 MB transferred with
ICU and is about 5.1 MB with `InvariantGlobalization`, under the 8 MB target.

Whatever the compression, the LGPL layout holds in the published `_framework/`: `ShotDetector.FastYuv.wasm` is its
own file (no single-file, no merged AOT) and `licenses/ShotDetector.FastYuv/COPYING.LGPL` is in the Pages artifact; the
deploy row checks both from the published listing. (Compiled ahead of time, FastYuv's code is also in
`dotnet.native.wasm`, so replacing it means rebuilding the bundle: [2026-10-24-fastyuv-replaceable.md](2026-10-24-fastyuv-replaceable.md).)

## Threads

### Question

ManagedCodecs decodes on several threads if asked, and ShotDetector scores chunks in parallel. Can the page use that?

### Choices

1. **No: single-threaded.** Wasm threads need `SharedArrayBuffer`, which needs COOP/COEP headers, which Pages cannot
   set.
2. **A service worker that adds the headers** (the `coi-serviceworker` trick) and a multithreaded runtime build.

### Answer

**1**, and 2 is a Maybe row with its enabler named. On one thread a trailer takes a few times real time on a laptop
(ManagedCodecs at 2.3 to 3.6 times FFmpeg's time), which is what the scope promised.

## The page itself

### Question

What is on the page, and with what?

### Choices

1. **One `index.html`, one `app.js`, one `style.css`, no build step, no framework, no dependencies.** A file picker
   that also takes a drop; the detector (adaptive, content, threshold, histogram, hash) with its threshold prefilled
   from ShotDetector's default, and the minimum shot length; a "Try the demo" button; opening and progress states with
   a cancel; the shots in a table (number, start, end, length), each row seeking a `<video>` element that plays the
   original file (the browser decodes for playback; exactness is about the numbers, not the picture); downloads of the
   scenes CSV and the stats CSV, named after the file; errors shown in the words the library throws. A footer: what
   runs where, that nothing leaves the machine, the licenses.
2. **A component framework** (Blazor was declined by the owner; React, Lit and the like are a build step).

### Answer

**1.** A visitor should read the page's source and see the whole thing. Stats are always collected (that is the
scenedetect `-s` output the exactness check compares; its memory is a few hundred bytes a frame).

## A damaged file's message

### Question

The page row asks for ManagedCodecs' `InvalidDataException` (a damaged file) to be shown prefixed "The file is damaged
or not an MP4 this page can read:", and every other error as the library throws it. But a .NET exception reaches
JavaScript as a `ManagedError` that carries the message and the .NET stack's frames, not the exception's type (seen
2026-10-24 in Chromium: `name` "Error", a stack starting in `H264Decoder.ParsePicture`). Where does the page learn
that an error was a damaged file? (Added by the page row, 2026-10-24.)

### Choices

1. **`Api` adds the prefix**: `Open` and `Detect` catch `InvalidDataException` and throw it again with the prefix in
   its message (the original as its inner exception). The worker and the page pass messages on as they come.
2. **The type crosses the boundary**: `Api` catches every exception and returns or throws something that names the
   type, the worker posts `{ message, type }`, and `app.js` picks the words. A second error channel for one prefix.
3. **`app.js` guesses from the message or the stack's frames**: breaks when ManagedCodecs words a message differently
   or a frame is renamed.

### Answer

**1.** Three lines in `Api.cs`, which the row's Where (the page's three files) didn't foresee; the page stays a
display of what .NET says. The words are the page's, so they live with the page's exports, not in the core library,
whose callers get ManagedCodecs' exception as it is.

## One wasm project

### Question

`tools/WasmCheck` is a browser-wasm executable run under Node that detects on the samples. The page needs another
browser-wasm project with `[JSExport]`. Two?

### Choices

1. **One: `src/ShotDetectorWeb.App` replaces WasmCheck.** Its `Program.cs` only keeps the runtime alive; the `Api`
   class holds the exports. `tools/check.sh wasm` publishes the App and runs `tools/app-check.mjs` under Node, which
   calls the same `Open` and `Detect` exports the worker calls, on every sample and run, and writes the CSVs the native
   check compares. The FFmpeg-not-loaded check becomes an export too (`LoadedAssemblies()`).
2. **Two projects**: WasmCheck as it is, the App beside it.

### Answer

**1.** The exactness check then runs the page's own entry points, so the thing deployed is the thing checked. Node
runs `getAssemblyExports` as the browser does; WasmCheck already proves `[JSImport]` under Node.

## The demo clip

### Question

The owner wants a clip on the page. Which, and where does it come from?

### Choices

1. **Sintel's trailer (Blender Foundation, CC-BY 3.0), built at deploy time.** The Pages workflow downloads the
   original from download.blender.org pinned by SHA-256 and re-encodes it with a recipe added to
   `tools/make-samples.sh` (today `SINTEL=` only copies a file it names `sintel_trailer-480p.mp4`): 8-bit 4:2:0
   progressive H.264, constant rate, 480p (854x480), around 10 MB. CI runs the same recipe, so the exactness check
   covers the very file the demo runs. The page credits it.
2. **The clip committed to the repository** (plain or LFS; Pages doesn't serve LFS objects).

### Answer

**1.** No binary in git, one recipe for the check and the demo. If the download ever goes away the deploy fails
loudly and the row says what to do (commit the re-encoded file then).

2. **From ManagedCodecs' frames**, converted to RGB in .NET and sent over.

### Answer

**1**, as a Next row. The first release has the table and the player.

## Testing the page

### Question

The exactness checks cover the library, and with "One wasm project" the App's exports. What checks the page?

### Choices

1. **Nothing automated in the first release; a Playwright smoke test next**: CI serves the published bundle, loads the
   page in Chromium, sets the file input to one sample, clicks detect, downloads the scenes CSV and compares it with
   the native check's.
2. **Playwright from the start.**

### Answer

**1.** The page is a few hundred lines of JS around checked exports; the browser test earns its CI minutes once the
page exists and is being changed.

## Not doing

- **WebCodecs** (the browser's own H.264 decoder) as a faster path: its output may differ between browsers and from
  FFmpeg's, which is the one thing this showcase is about. Reopened for measurement (2026-10-26,
  [#15](https://github.com/bisforboman/shotdetector-web/issues/15); backlog "WebCodecs: are its frames ManagedCodecs'
  frames?"): this stands unless every frame is shown identical in each browser. Measured 2026-10-26 (below): it
  stands. Chromium's frames are ManagedCodecs' frames, every one of them; Firefox's reach the page in RGB.
- **Exports of clips or images through ShotDetector's `Export`**: it needs ffmpeg.
- **Analytics, a backend, uploads**: nothing leaves the machine; the page says so.

### WebCodecs, measured (2026-10-26)

Measured with `tools/webcodecs/` (README "WebCodecs") on a 4-core cloud VM without a GPU, headless, on Linux: Chromium
153.0.8010.12 (Playwright's build) and Firefox 136.0 (Ubuntu's build, through Puppeteer over WebDriver BiDi). Safari
wasn't run. The files: every sample of `tools/make-samples.sh` (made with Ubuntu's FFmpeg 6.1 and its libx264), Sintel's
trailer among them, and a two-hour film (that trailer looped to 7,200 s by libx264 at 640x360, 24 fps, 2.5 Mbit/s,
with AAC: 172,800 frames, 2.37 GB). Each browser's `VideoDecoder` got the access units ManagedCodecs' `Mp4Demuxer`
gives, and each frame's Y, U and V planes, copied out with `copyTo` as I420, were compared with those of the frames
`Mp4Input` decodes, frame by frame (a SHA-256 per plane), the timestamps too.

**The decoders.** Chromium: `isConfigSupported` says no to `prefer-hardware` and yes to `prefer-software` and
`no-preference`, for every sample's profile and level, so it decoded in software (Chromium's own build of FFmpeg's h264
decoder; there is no GPU here). Firefox: `isConfigSupported` says yes to all three, but its media log
(`MOZ_LOG=PlatformDecoderModule:5,FFmpegVideo:5`) shows one decoder for all of them: the system's FFmpeg (libavcodec
60, FFmpeg 6.1 here), `IsHardwareAccelerated=0`, in its RDD process, decoding into YUV 4:2:0 pictures.

**Chromium 153**, `prefer-software` (`prefer-hardware` not supported):

| Sample | Frames | As decoded (`format`, coded size, visible rect) | Result |
| --- | --- | --- | --- |
| baseline-480x270-23976-bt601 | 144 | I420 480x290, 480x270 at 0,0 | every frame identical |
| cuts-1280x720-25 | 75 | I420 1280x738, 1280x720 at 0,0 | every frame identical |
| cuts-640x360-2997-bt709 | 180 | I420 640x386, 640x360 at 0,0 | every frame identical |
| cuts-854x480-25 | 150 | I420 864x482, 854x480 at 0,0 | every frame identical |
| edit-end-352x288-25 | 75 (of 114 units, 39 discarded) | I420 352x290, 352x288 at 0,0 | every frame identical |
| fades-320x240-25 | 160 | I420 320x258, 320x240 at 0,0 | every frame identical |
| full-range-320x240-25 | 114 | I420 320x258, 320x240 at 0,0 | every frame identical |
| sintel_trailer-480p | 1,253 | I420 864x482, 854x480 at 0,0 | every frame identical |
| start-offset-352x288-25 | 114 | I420 352x290, 352x288 at 0,0 | every frame identical |
| tone-silence-320x240-25 | 375 | I420 320x258, 320x240 at 0,0 | every frame identical |

| the two-hour film | 172,800 | I420 640x386, 640x360 at 0,0 | every frame identical |

Every plane of every frame equal, in display order, each frame's timestamp the pts ManagedCodecs gives it.

**Firefox 136**, `prefer-software` and `prefer-hardware` alike, on every sample and the film: **differs**. The first
frame, and every one after it, reaches the page as `BGRX` (the visible size as the coded size: 854x480 for the
trailer), so `copyTo` refuses I420 ("I420 is unsupported in ParseVideoFrameCopyToOptions"): Firefox converts its
decoder's YUV to RGB before the page sees a frame, with its own conversion, and there are no Y, U and V planes to
compare, nor ShotDetector's FastYuv conversion to keep. Decoding in the content process (`media.rdd-process.enabled`
false) makes H.264 unsupported, and turning off the GPU process or remote textures leaves the frames BGRX. A visitor's
Firefox with a GPU, or on another system, may differ again; nothing here says it gives YUV.

**The timings**, decode plus the copy out (WebCodecs) against ManagedCodecs' `H264Decoder` on wasm AOT, fed the same
access units in the same browser, each run in a worker of its own, the runs alternating; the trailer the median of
three, the film once:

| Browser | File | WebCodecs, decode + copy | ManagedCodecs, wasm AOT | |
| --- | --- | --- | --- | --- |
| Chromium 153 | Sintel's trailer (1,253 frames, 854x480) | 1.71 s (733 fps) | 16.65 s (75 fps) | 9.7 times faster |
| Chromium 153 | the two-hour film (172,800 frames, 640x360) | 243 s (712 fps) | 1,656 s (104 fps) | 6.8 times faster |
| Firefox 136 | Sintel's trailer | 12.92 s (97 fps; `prefer-hardware` 12.12 s, the same decoder) | 20.57 s (61 fps) | 1.6 times faster |
| Firefox 136 | the two-hour film | 410 s (422 fps) | 1,929 s (90 fps) | 4.7 times faster |

Firefox's WebCodecs times include its conversion to RGB. Its first trailer run took 26.7 s: it came right after the
film's compare pass, which stopped at its first frame and left the film's download running (the tool cancels it since).
Chromium's decoder uses several threads, which ManagedCodecs on wasm can't. Decoding is most of a run (the page's
trailer run takes 20.8 s in Chromium), so in Chromium a run might take under a third of its time with WebCodecs (20.8 - 16.65 + 1.71 s); that is
an estimate from these numbers, not a measured run.

**The verdict.** The decision changes only if every frame is identical in both browsers: in Chromium every frame is,
in Firefox there are no YUV frames at all. So WebCodecs stays out of the page, and no row builds it. Using it in
Chromium alone, with ManagedCodecs everywhere else, would be a new question (one browser's path differing from the
others', a GPU's decoder under `no-preference`, which this VM couldn't try): the owner's to open, not this
measurement's.
