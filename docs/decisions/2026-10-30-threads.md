# Threads in the browser, and the page offline (2026-10-30)

Backlog "Threads in the browser" and "Offline (a service worker caching the bundle)", both chosen by the owner on
2026-10-30. The threads row asks for this decision before any code. Everything below was measured on 2026-10-30 against
`main` at `46d3587` (ShotDetector 3.20.0, ManagedCodecs 0.1.0, .NET 10.0.14's runtime packs), with a throwaway
prototype that is not in the repository: `Mp4Input` handing a thread count to `H264Decoder.Threads`, and two exports, one
setting the count and one opening a file from bytes.

## What was found

### ManagedCodecs' `Threads`, through the core

`H264Decoder.Threads` is frame threading: each picture decoded on a thread of its own, waiting only for the rows of its
references that its motion vectors reach, and giving the same frames (ManagedCodecs' documentation; 1, the default,
decodes on the calling thread, "as WebAssembly in a browser needs"). With more than 1, `Decode` returns frames up to
that many packets later (`Flush` gives the rest) and blocks on a monitor while it waits for a free decoder.

The core doesn't reach it today: `Mp4Input.DecodedFrames` makes `new H264Decoder(info)` and nothing sets `Threads`. It
is a property to add (`Mp4Input.DecoderThreads`, or a parameter of `Open`), passed to every decoder `Mp4Input` makes
(`Frames`, `FramesAsync`, `ScoreRangeAsync`); the frames and their order don't change, so `Detect` and `ScoreRange` see
the same input. Only decoding gets faster: ShotDetector reads a frame source once and in order (`DetectionMode.Parallel`
is for its file path), and FastYuv's conversion and the detectors stay on the run's thread.

### What `WasmEnableThreads` does to the bundle

`-p:WasmEnableThreads=true` swaps in the runtime pack `Microsoft.NETCore.App.Runtime.Mono.multithread.browser-wasm`
(Emscripten pthreads: the wasm memory is a `SharedArrayBuffer`, each .NET thread a Web Worker the runtime starts from
`dotnet.native.worker.mjs`). Both builds publish with `-warnaserror`, interpreted and AOT. `_framework/`, files through
`gzip -6` as README "Size" counts them:

| Publish | Raw | Compressed | `dotnet.native.wasm` raw |
| --- | --- | --- | --- |
| Interpreted, today | 7.12 MB | 2.75 MB | 3.00 MB |
| Interpreted, threads | 7.34 MB | 2.82 MB (+69 KB, +2.5%) | 3.09 MB |
| AOT, today | 19.24 MB | 5.78 MB | 15.05 MB |
| AOT, threads | 19.82 MB | 5.93 MB (+154 KB, +2.7%) | 15.56 MB |

The bundle itself costs little, but the threaded runtime has three requirements that matter more:

1. **It must start on the page's main thread, not in a Web Worker.** Started from `worker.js`, as the page starts its
   runtime today, it fails: `dotnet.js` takes a worker whose `onmessage` isn't set yet when the module loads for one of
   its own pthreads (`dotnetSidecar`), and with `dotnet.js` imported after `onmessage` it asserts on its thread ids
   (`mono_wasm_pthread_ptr ... threadId from thread info 0`). Started on the main thread, .NET 10 runs managed code on a
   "deputy" thread (a worker of its own) and dispatches each export to it. By default it refuses synchronous exports
   from the main thread ("Cannot call synchronous C# methods"; `jsThreadBlockingMode` `PreventSynchronousJSExport`).
   `Open`, `Stop`, `ScenesCsv` and the other synchronous exports would become `Task`s. And the main thread has no
   `FileReaderSync`, which `BlobStream` reads the picked file with. The prototype skipped that by opening the file from
   bytes in memory. How a real run would read the `File` from the deputy thread, in slices, is not worked out.
2. **It needs `SharedArrayBuffer`, so cross-origin isolation.** Without COOP/COEP it doesn't start at all ("SharedArrayBuffer
   is not enabled on this page"), whatever the thread count. There is no falling back to one thread within the same
   bundle: a fallback is the single-threaded bundle as well, published next to it.
3. **It doesn't run under Node** ("This build of dotnet is multi-threaded, it doesn't support shell environments like
   V8 or NodeJS"). `tools/app-check.mjs` couldn't check it. Only a check in Chromium (`tools/page-check`) could.

### Cross-origin isolation on GitHub Pages

Pages can't set response headers. The `coi-serviceworker` trick is a service worker that re-serves every response of
its scope with `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` (or
`credentialless`). The page registers it and reloads once when it first takes control, after which `crossOriginIsolated`
is true. Everything the page loads is same-origin (its scripts, `_framework/`, the demo clip), and the links out are
navigations, so COEP breaks nothing on it. Where service workers are unavailable (some private modes) or the reload
doesn't happen, the page isn't isolated and would need the single-threaded bundle. The repository's page has no
dependencies, so this would be a few lines of its own (`sw.js`), not the `coi-serviceworker` package.

### The speed gain

The prototype ran in headless Chromium 153 on this 4-core cloud VM, AOT, with the runtime on the page's main thread,
the file opened from memory and `Detect` with the page's defaults (adaptive), timed from the call to its answer. Each
round ran every configuration once, in alternating order (interleaved, so the VM's drift falls on all of them alike):

| Video | Rounds | Today's bundle | Threads bundle, 1 | 2 | 4 | 6 |
| --- | --- | --- | --- | --- | --- | --- |
| Sintel's trailer, 854x480 (the demo, 1,253 frames) | 5 | 17.87 s | 18.96 s | 9.36 s | **6.96 s** | 7.07 s |
| The same at 1280x720 (libx264 CRF 23 from Blender's 1080p) | 4 | 23.35 s | 24.45 s | — | **8.97 s** | 9.00 s |

Medians. Four decoder threads made the run 2.6 times as fast at both sizes, and six did no better on four cores. The
threaded runtime on one thread is about 5% slower than today's. Every run's scenes CSV was the same as the first
one's. For comparison, the same trailer split across four workers took 6.7 s (README "Long videos across workers",
2026-10-27, through the page's worker and `Blob`), so threads and splitting reach about the same speed on four cores.
The difference is that threads keep the live shot table and one runtime's memory.

One run hung: the threaded bundle on one thread, at 720p, at 100% CPU for over 15 minutes, until it was killed. It
didn't happen again in the 35 other threaded runs. That isn't explained, and a build would need to be checked against it.

### With the split across workers

A split run (over `SPLIT_SECONDS`, 2 minutes, across up to `MOST_WORKERS`, 4) gives each range a Web Worker with its own
runtime, and the threaded runtime can't start in a worker, so split runs would keep today's bundle. The two don't add
up either: four workers already keep four cores busy, and threads in each would only add contention. So threads would
apply to one-worker runs, which are videos up to 2 minutes and runs forced to one worker with `?workers=1`. The sound's
worker would stay on today's bundle too, so a page with threads loads both runtimes on a file's first run (about
5.9 + 5.8 MB compressed on a first visit, where today it is 5.8).

### The offline cache

With a service worker (needed for threads or not), caching what the page loads takes a few more lines. The page works
offline once the cache holds:

- the page's own files: `index.html`, `style.css`, `app.js`, `timeline.js`, `versions.js`, `worker.js`,
  `blob-read.js`, `blob-write.js`, `pause.js` and `panels/*.js`;
- `_framework/`: every file `dotnet.js` loads (about 19 MB raw for the AOT bundle, twice that with a second bundle);
- the license under `licenses/`, and the demo clip (`demo/sintel-trailer.mp4`, 10 MB) if it is cached at all.

The user's own files never go through it: they are `Blob`s read in the worker.

`_framework/` keeps unhashed names (`WasmFingerprintAssets` false, for FastYuv's replaceable `.wasm`), so a new
deploy changes files without renaming them. Pages answers with `max-age=600` and an ETag. A cache that keeps a
`dotnet.js` from one deploy with a `dotnet.native.wasm` from another breaks the runtime's start, so how the cache learns
of a new deploy is the question below.

## Threads

### Question

The decoder's threads make a one-worker run about 2.6 times as fast on four cores, with the same results. Getting them
means the threaded runtime on the page's main thread instead of in its worker, cross-origin isolation through a service
worker, today's bundle kept for split runs, the sound and browsers without isolation, and a check of the threaded
bundle in Chromium only. Build it?

### Choices

1. **Not now.** Record what was measured here, and move the row to backlog-done.md as Won't do until .NET's threaded
   runtime starts in a Web Worker. Splitting stays the page's way to use more cores.
2. **Build it for one-worker runs.** The threaded bundle on the page's main thread runs videos up to 2 minutes with
   `Threads` set from `navigator.hardwareConcurrency` (4 at most, as measured). Today's bundle stays in workers for
   split runs, the sound, and pages that aren't isolated. Every export becomes asynchronous on the threaded side, the
   file is read from the deputy thread (not worked out yet), both bundles are published and checked (an AOT build
   more in CI and `pages.yml`), and the page check runs the threaded bundle's CSVs against the native run's. This
   reverses the earlier decision to decode in a web worker for those runs.
3. **The same speed by splitting.** Lower `SPLIT_SECONDS` so that short videos split across workers too. That reaches
   about the same speed on four cores with no new runtime and no isolation, but gives up the live shot table on those
   runs (the 2026-10-26 workers decision kept it for videos under 2 minutes). This would be a new row, measured.

### Answer

**2**, the owner's choice (2026-10-30). How it is built is under "As built" below.

### As built (2026-10-30)

The decision's "What was found" left one thing open: how the threaded runtime reads the file on the main thread. A
`[JSImport]` called from .NET's JavaScript thread (the deputy) runs on the page's thread, which has no `FileReaderSync`,
and .NET refuses to call JavaScript synchronously from inside a synchronous export. So in the threaded bundle
(`THREADS`), `Host.cs` puts the run on the thread pool and hands every call into JavaScript back to the JavaScript
thread in order: progress and shots posted, the pause awaited, and each megabyte of the file read with
`Blob.arrayBuffer()` there and copied in while the pool's thread waits. Opening goes the same way. The exports the
page's thread calls are tasks (`Api.Threads.cs`). In the worker's bundle `Host` calls straight through, and nothing
changed for `app-check.mjs`.

- `Mp4Input.DecoderThreads` sets the decoder's threads. `H264Decoder` isn't disposable, so frames that end early (a
  stop, a cancel, a range's end) flush it, and its threads finish the pictures they were given and end (ManagedCodecs
  0.2.3's threads otherwise end after an idle timeout). NativeCheck's
  `ThreadsCheck.cs` runs every sample's all-detector run on four threads, whole, in ranges and stopped half-way,
  against one thread: byte for byte on every sample.
- `threads.js` is the threaded runtime on the page's thread: a runner with `worker.js`'s messages, so `app.js` hands it
  a one-worker run as it would its worker. The runner opens the file for itself (the page's worker keeps it open too,
  for the panels and the next split run). It can't be terminated: one that doesn't answer a stop is abandoned, and runs
  go on the page's worker until a reload. If the threaded runtime doesn't start, the run goes on the page's worker.
- `sw.js` adds COOP and COEP to every same-origin response and keeps each whole answer in the cache, network first.
  `app.js` registers it and reloads a first visit once when it takes over, unless a file has been picked by then.
- `tools/check.sh` publishes both bundles (`publish_app`), the threaded one into `wwwroot/threads/_framework/`, and
  `pages.yml` deploys both and checks the site has each one's FastYuv. The threaded bundle doesn't run under Node, so
  the page check is its check. Every page there is first isolated by its service worker. The sample runs on threads,
  on the page's worker (`?threads=0`) and on two workers. The demo runs on threads, paused, resumed, and stopped while
  paused. Then the page is reloaded offline and the demo runs again from the cache. Every run's CSVs equal the native
  ones.

### Measured again (2026-10-30)

`main` moved to ManagedCodecs 0.2.3, whose decoder is much faster, while this was built, so the gain was measured
again on the page itself (`?threads=0`, `?threads=2` and the default 4 on the same published AOT bundles, fresh pages
each isolated by the service worker, in interleaved rounds, headless Chromium on the same 4-core VM, the medians):

| Video | Rounds | The page's worker | 2 threads | 4 threads |
| --- | --- | --- | --- | --- |
| Sintel's trailer, 854x480 | 5 | 13.7 s | 9.6 s (1.43 times as fast) | 8.5 s (1.61) |
| The same at 1280x720 | 4 | 19.1 s | — | 10.3 s (1.85) |

The decoder is now a smaller part of a run, so threads save less of it than 0.1.0's 2.6 times. These are the estimate's
`THREADS_SPEEDUP`, measured again with the reference rate later that day (16.7 s, 12.0 s and 11.1 s: 1.39 and 1.50,
README "Large files"). The prototype's hang wasn't seen again. A crash was: the threaded runtime ended
(`ReleaseJSOwnedObjectByGCHandle`, "Process terminated") once the file's slices were copied into an `ArraySegment`,
whose view .NET pins behind a handle that the collector later releases on another thread. A `Span`'s view, which lives
for the call only, fixed it. A runtime that ends still fails the run with why and turns threads off (`threads.js`,
`onAbort`).

## The offline cache

### Question

How does the service worker cache the page and its bundle, and how does a new deploy reach a visitor?

### Choices

1. **Network first, the cache as the fallback.** Online, every request goes to the network, through the browser's HTTP
   cache as today, and its answer replaces the cached copy. Offline, the cached copy answers. A deploy reaches a visitor
   exactly as it does today. There is no list of files and no version to keep. A visit cut off half-way through loading
   a new deploy can leave a mixed set that fails offline until the next online visit.
2. **Cache first, by deploy.** `pages.yml` writes the deploy's commit into the service worker, which caches the whole
   bundle under that name at install, answers from it, and drops the old cache once the new one is complete. Repeat
   visits don't wait for the network, and a set is never mixed, but a new deploy shows on the visit after the one that
   fetched it. It also needs the bundle's file list at install (from the publish), and the page check has to set a
   version too.
3. **No offline.** No service worker unless threads need one.

### Answer

**1**, the owner's choice (2026-10-30). The same service worker adds the isolation headers.

## The demo clip offline

### Question

The demo is Sintel's trailer, 10 MB. Does the offline cache hold it?

### Choices

1. **Once it has been played.** It is cached when a visitor first runs the demo, like any other response.
2. **Never.** Offline, the page runs the visitor's own files only, and the demo button says it needs the network.
3. **Always.** Fetched with the bundle on the first visit, 10 MB more for every visitor.

### Answer

**1**, the owner's choice (2026-10-30): network first, like everything else, so the demo is cached once a visitor has
fetched it.
