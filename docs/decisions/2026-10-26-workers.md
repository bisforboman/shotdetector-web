# Long videos across several Web Workers (2026-10-26)

ShotDetector 3.16.0 can score a video in ranges, each on a runtime of its own (`ShotDetection.ScoreRange` and
`ScoreRangeAsync`), and merge the ranges' scores (`RangeScores`, carried between workers as bytes) into exactly the
result `Detect` gives for the whole video (`ShotDetection.Merge`). Workers need no shared memory, so this works on
GitHub Pages, unlike wasm threads. Issue [#19](https://github.com/bisforboman/shotdetector-web/issues/19); backlog
"Long videos across several Web Workers". The owner answered each question below on 2026-10-26.

## What the page shows during a run

### Question

With one worker, shots appear as they are found (`DetectionOptions.OnShot`). With several, shots exist only after
`Merge`. What does the page show meanwhile?

### Choices

1. **Progress per range, the shots at the end.** The timeline shows each worker's range and how far it has got. The
   table fills in once the ranges merge. A run with one worker keeps today's live shots.
2. **Always one worker** unless the user asks for speed, so live shots never go away by default.

### Answer

**1.**

## What Stop does

### Question

Stop (backlog "Stop a run and keep what was read, without restarting the worker") ends a one-worker run
with a result for the frames read so far. What does it do when several workers are running?

### Choices

1. **Keep the finished start.** Merge the ranges finished from the start of the video onward, without a gap, and
   show their shots and stats as stopped there. Ranges still running, and finished ones after a gap, are dropped.
2. **Drop everything**, as today.

### Answer

**1.** `Merge` takes the ranges given, so a prefix of them merges to the result for that part of the video.

### As built (2026-10-27)

Stop stops every worker at its next pause, as a one-worker run's Stop does, and each range ends where its worker got
to ("the range ends where the frames stop", ShotDetector's `ScoreRange`). The ranges merged are those from the start
while each reaches into the next one's first frame (`Mp4Input.FromStart`): the first range that stopped short is the
last one merged, up to where it stopped, and everything after it is dropped. So "finished from the start" counts the
first unfinished range's frames read too: the ranges are about equal in frames and run side by side, so they all
finish near the end, and keeping only finished ones would keep nothing until then. The result is the one for a video
that ends where that range stopped, as a one-worker run's stop is (`tools/app-check.mjs` stops runs in their second
range and checks it against the whole run as it checks a stopped run). A worker that doesn't answer the stop within a
second or so is terminated and its range left out (a gap), unless it is the page's own worker, which merges: then the
run is lost as a one-worker run whose worker doesn't answer is.

## When to split

### Question

How many workers, and from what length on?

### Choices

1. **Long videos, cores to spare.** Above about 10 minutes of video: up to `navigator.hardwareConcurrency` − 1
   workers, at most 4, each range starting at a keyframe (from the packet list, "Packets in the core"), the ranges
   about equal in frames. Shorter videos keep one worker. The numbers are a starting point, to be measured.
2. **Only when asked**: a "Use N workers" option, off by default.

### Answer

**1.** The row measures the two-hour film with 1, 2 and 4 workers and adjusts the 10 minutes and the 4 to what it
finds, saying so here.

### As measured (2026-10-27)

README "Long videos across workers" has the table: on the two-hour film (AOT, headless Chromium, a 4-core cloud VM),
2, 3 and 4 workers ran 1.97, 2.93 and 3.60 times as fast as one (1,323 s, 672 s, 451 s, 368 s), the same CSVs every
time, and took the renderer from 878 MB to 1,065, 1,303 and 1,602 MB: each worker's runtime holds its own copy of
ManagedCodecs' sample index (174 MB of wasm heap once the film is open, 208 MB at the end of its range).

- **The 10 minutes became 2.** Splitting paid on every length measured, down to Sintel's 52 s trailer (19.0 s on one
  worker, 6.7 s on four), so length is no reason to keep one worker; what a split run gives up is the live shots
  (the first question's answer). Below 2 minutes a one-worker run is short enough to keep them (the trailer's 19 s,
  the demo's), above it the wait is worth shortening.
- **The 4 stays 4.** The speed grew almost linearly up to the 4 cores measured, but the memory grew by 190 to 300 MB a
  worker on the film, 1.6 GB at 4; a fifth and sixth would take a film past 2 GB, and a machine with more than 4
  cores wasn't there to measure what they would give. Worth raising once the index is smaller (backlog, Waiting:
  "ManagedCodecs: the MP4 index without its copies").
- **For the owner, not changed:** `hardwareConcurrency` − 1 leaves a core for the page. On the 4-core VM the page
  picks 3 workers; 4 (forced with `?workers=4`) ran 23% faster still (368 s against 451 s), at 300 MB more, the
  sound's own worker slowed (78 s instead of 60) but done long before the run. Using every core is a one-line change
  in `app.js` if the owner wants it.

## The audio pass

### Question

The waveform and the sound measures (`Api.Audio`) run after detection today. Should they run in a worker of their
own, at the same time?

### Choices

1. **Yes, in parallel.** The audio pass doesn't depend on detection. It finishes alongside it instead of after, at
   the cost of one more runtime in memory.
2. **No, after detection**, as today.

### Answer

**1.**, also with one detection worker.

### As built (2026-10-27)

`app.js` starts the sound's worker as the file's first run starts: it opens the same `File` and calls `Audio`, and its
answer is told to the panels as before (`audio`). On the two-hour film the sound came 52 s into a 1,323 s one-worker
run, where it used to come after the run.
