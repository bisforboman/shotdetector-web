# MJPEG in AVI (2026-10-30)

Backlog "MJPEG in AVI", chosen by the owner on 2026-10-30. Today the core reads only MP4 (`Mp4Input`, `Mp4Header`,
`SpsInfo`). The row is a design question first: an AVI input beside `Mp4Input`, or a common input type; what `YuvVideo`
FFmpeg reports for an AVI; the packets, ranges and the page's exports.

Measured on 2026-10-30 against `main` at `e2c3e1b` (ShotDetector 3.22.0, FastYuv 3.22.0, ManagedCodecs 0.2.4 with
`ManagedCodecs.Mjpeg` 0.2.4, the version the other three pin), with FFmpeg 8.1.3 (BtbN's shared build the checks pin)
and a throwaway console program, not in the repository: `AviDemuxer` and `MjpegDecoder` giving `YuvFrame`s to
`Detect(YuvVideo, ...)` under FFmpeg's own description, every detector against `Detect(path)` in-process with the same
converter. Files made for the purpose: `testsrc2`, `mandelbrot` and `smptehdbars` cut together, `-c:v mjpeg` in AVI.

## What was found

### 4:2:0 MJPEG in AVI agrees already

On 320x240 at 25 fps and 640x360 at 30000/1001, `format=yuvj420p` (or `yuv420p` with `-color_range pc`, which comes out
the same), with no audio or with PCM audio: every detector's scenes CSV, stats CSV, shots JSON and HTML were the FFmpeg
path's byte for byte, and the FFmpeg path decoded in-process. Nothing upstream for these.

What FFmpeg says about such a file, and so what `YuvVideo` must say:

| Field | FFmpeg | Where the core gets it |
| --- | --- | --- |
| `pix_fmt` | `yuvj420p` (mjpegdec: a JPEG is full range) | the decoder's frame format (`Yuv420P`) and JPEG's full range: always `yuvj420p` |
| `color_range`, `FullRange` | `pc` | always true |
| `color_space` | `bt470bg` (mjpegdec tags every YUV JPEG BT.601) | always `bt470bg` |
| `time_base` | the video `strh`'s `dwScale/dwRate`, reduced: 1/25, 1001/30000 | `AviDemuxer`'s `TimeBase` |
| `avg_frame_rate` | `dwRate/dwScale`: 25/1, 30000/1001 | the time base, inverted |
| `start_pts` | 0 | the first packet's pts |
| `nb_frames` (`FrameCount`) | the `strh`'s `dwLength`: 114 | `AviDemuxer`'s `FrameCount` |
| format duration | the longest stream: the video's `dwLength × dwScale / dwRate` (4.560000, 4.504500), or an audio stream's (below) | the headers |
| codec, container | `mjpeg`, `avi` | constants |
| size | the SOF's | the first decoded frame |

Every MJPEG packet is a keyframe (FFmpeg's `K` flag for each, which `AviDemuxer` gives too: it reads no index), so a
long AVI splits into ranges wherever an equal split falls (`Ranges`), each range decoded from its own first frame.

### 4:2:2 MJPEG: out of scope, ShotDetector first

`yuvj422p` (most cameras' MJPEG) decodes in ManagedCodecs (`PixelFormat.Yuv422P`), and FastYuv converts it: its
`SwscaleYuv420` implements ShotDetector's `IYuv422Converter`, which the file path uses. The frame-source path doesn't take
it: `Detect(YuvVideo, ...)` on a `yuvj422p` file throws "Frames from the caller must be yuv420p or yuvj420p so far, not
yuvj422p." (3.22.0). So 4:2:2 MJPEG waits for the backlog's "10-bit 4:2:0 and 8-bit 4:2:2" row, whose upstream ask
(`YuvFrame` with 4:2:2 chroma, `YuvVideo.PixelFormat` accepting it) covers it; until then the core refuses it with its
own message, as it refuses 4:2:2 H.264. 4:4:4 (ffmpeg's `-c:v mjpeg` of an RGB source, without `format=`) the same.

### A dropped frame: ManagedCodecs' timestamps, and the frame source's grid

ffmpeg's AVI muxer, interleaving MP3 or AAC, wrote an empty `00dc` chunk (a dropped frame) after the first frame. FFmpeg
counts it: the next packets' pts are 2, 3, ... and `nb_frames` is the header's 51 for 50 packets. ManagedCodecs'
`AviDemuxer` skips the chunk without counting it: its pts are 0, 1, 2, ..., not FFmpeg's (it says it gives FFmpeg's
timestamps). And even with FFmpeg's pts the frame-source path would refuse the gap ("dropped frames aren't supported
yet", `VideoReader.CheckConstantRate`), the variable-rate issue's third point (shotdetector#609). With ManagedCodecs' pts
the stats CSVs differed from the FFmpeg path's from frame 1 on.

So the core refuses an AVI whose video chunks are fewer than its header's `dwLength` ("drops frames"): the count the
demuxer's packets give against `FrameCount`. The same check refuses an OpenDML file over 1 GB, whose `AVIX` parts
`AviDemuxer` doesn't read (its packets stop at the first part, the header's count goes on). The ManagedCodecs half is a
bug to report there (below), not to work around here.

### Audio in AVI

`AviDemuxer` exposes no audio (`Audio` is always null), and FFmpeg's format duration counts the audio's: 3.030204 s
for 2 s of video with 3 s of MP3, 3.041814 s with AAC, where a variable-bitrate audio stream's `strh` (`dwSampleSize` 0)
gives its duration as `dwLength × dwScale / dwRate`. For PCM and IMA ADPCM (`dwSampleSize` set) FFmpeg gives the stream
no duration (`N/A`) and the format's is the video's. ffprobe names the codec from the `strf`'s `wFormatTag` (and bits
per sample for PCM): `pcm_s16le`, `pcm_u8`, `adpcm_ima_wav`, `mp3`, `aac`, ...

So an AVI with audio needs the audio streams' headers read here (an `AviHeader`, as `Mp4Header` reads what
`Mp4Demuxer` doesn't expose): the duration, and `Audio`'s codec, rate and channels as ffprobe gives them. Measuring it
(`Mp4Audio`, AAC only) is another matter: PCM would be the measure's own decoder, which the core doesn't have.

### Interlaced MJPEG

ffmpeg's MJPEG encoder doesn't write interlaced (AVI1 two-field) packets ("interlacing not supported by codec"), so no
sample can be made with the recipe's tools; `MjpegDecoder` weaves them as FFmpeg does. Left unchecked, said so in the
README's scope.

### The page

No browser plays MJPEG in AVI: the `<video>` beside the cards and the stills of the shots' table stay empty. Each MJPEG
packet is a JPEG the browser does show, though: an `<img>` of the packet at the playhead (and of each shot's middle
frame for the table) would be the picture, without sound.

## The shape

What `Mp4Input` does today splits in two:

- per container: the description (`Mp4Header`, `SpsInfo`, the walk for the format duration and `Packets`) and the frames
  (a demuxer and a decoder: `Mp4Demuxer` and `H264Decoder`; `AviDemuxer` and `MjpegDecoder`);
- the rest, which never looks at the container: `Detect`, `DetectAsync`, `FramesAsync`, pausing, the picture's meter,
  `Ranges`, `ScoreRangeAsync`, `Merge`, `FromStart`, `ShownFrames`, `DecoderThreads` (H.264's; MJPEG decodes on the
  calling thread).

Three ways to shape that:

1. **A common base**: `VideoInput`, abstract, with the shared part (and `VideoInput.Open`, picking the container by the
   file's first bytes, as ManagedCodecs' `Demuxer.Open`); `Mp4Input` and `AviInput` derive from it, each its
   description and its frames. The App, NativeCheck and app-check hold a `VideoInput`; nothing on the page changes but
   the file filter and the damaged-file message. `Mp4Input.cs` keeps its file and name (less to conflict with the
   sessions on interlaced H.264 and resume), the shared code moves to `VideoInput.cs` and `VideoInput.Ranges.cs`.
2. **One class renamed**: `Mp4Input` becomes `VideoInput`, the container a private strategy inside it. The same split,
   one public type; a rename across the repository (README, CLAUDE.md, every check).
3. **`AviInput` beside `Mp4Input`**, nothing shared: the ranges, pausing and detection copied, the App branching on the
   type at each export. The smallest diff to `Mp4Input`, the most code to keep equal.

## Choices

Put to the owner with AskUserQuestion on 2026-10-30; the owner chose the recommended answer to each.

1. **The shape:** chosen: 1, a common base `VideoInput` with `Mp4Input` and `AviInput`.
2. **AVI with audio:** chosen: taken: `AviHeader` reads the audio streams' headers for the format duration and
   `Audio` as ffprobe's, checked by NativeCheck's description and audio-stream checks on a PCM and an MP3 sample; the
   sound not measured ("only AAC in MP4 is measured so far"). Or refused for now, with a row for it.
3. **The page with an AVI:** chosen: a line in place of the video ("The browser can't play this file: the
   analysis is the same"), no stills, and a backlog row for the picture from the file's own JPEGs. Or the `<img>`
   picture and stills in this PR. Built by the backlog row on 2026-10-31: the JPEGs cut from the picked file by the
   page where `Packets()` says each chunk's data starts, rather than an `Api.Frame(index)` export, which would wait
   behind a run on the page's worker (the owner's choice that day).
4. **ManagedCodecs' empty chunk:** chosen: an issue filed in bisforboman/ManagedCodecs by the session, the draft
   below; or left for the owner to file.

## Upstream issue

Filed by the session on 2026-10-30 as
[ManagedCodecs#226](https://github.com/bisforboman/ManagedCodecs/issues/226), from this draft:

> **Title:** AviDemuxer: an empty video chunk (a dropped frame) isn't counted in the pts
>
> FFmpeg's AVI demuxer counts a zero-size `00dc` chunk as a frame: no packet comes out for it, but the next packet's pts
> is one more (ffprobe's packets of the file below: pts 0, 2, 3, ...; `nb_frames` 51, the header's `dwLength`, for 50
> packets). `AviDemuxer` skips it without counting: its packets have pts 0, 1, 2, ..., so every frame after a dropped
> one is a frame early against FFmpeg's timestamps.
>
> Reproduce (FFmpeg 8.1.3): `ffmpeg -f lavfi -i testsrc2=s=320x240:r=25:d=2,format=yuvj420p -f lavfi -i sine=d=3 -c:v
> mjpeg -c:a libmp3lame drop.avi` (the muxer writes an empty `00dc` after the first frame), then compare
> `ffprobe -select_streams v -show_entries packet=pts drop.avi` with `AviDemuxer`'s packets.
>
> Asked: the pts as FFmpeg's (an empty chunk advances the frame counter). Found by shotdetector-web's "MJPEG in AVI" row
> (decision `2026-10-30-mjpeg-avi.md` there), which refuses such files meanwhile.
